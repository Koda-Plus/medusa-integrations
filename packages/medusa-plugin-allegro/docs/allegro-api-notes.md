The Medusa side (order import, tax lines, reservations, payments, fulfillment and shipment subscribers, cancellations, the shared lock, every admin route and the admin page) ran end to end in demo mode on a local Medusa 2.15.3 with Postgres 16 on 2026-10-06.

## Authentication, scopes, limits

- Device flow: `POST https://allegro.pl/auth/oauth/device?client_id={client_id}` with HTTP Basic (`client_id:client_secret`) and an optional `scope` form parameter, scopes separated by spaces. The answer has `user_code`, `device_code`, `verification_uri_complete`, `expires_in` and `interval`. Polling `POST /auth/oauth/token` with `grant_type=urn:ietf:params:oauth:grant-type:device_code` answers `authorization_pending`, `slow_down`, `access_denied` or "Invalid device code" (code invalid or already used). Source: authentication tutorial.
- App registration (apps.developer.allegro.pl, sandbox apps.developer.allegro.pl.allegrosandbox.pl): name, optional short description, the type "Aplikacja będzie działać w środowisku bez dostępu do przeglądarki albo klawiatury" for the device flow, redirect addresses (not needed for the device flow) and the terms. "Na jednym koncie możesz posiadać do 5 kluczy aplikacji jednocześnie." Scopes are not picked in the form; the app asks for them in the request. Source: Polish authentication tutorial.
- Narrower scope: "dostaniesz uprawnienie tylko na te funkcjonalności, które podałeś". The token answer carries `scope`. A refresh keeps the scope of the consent, so a scope the consent does not hold needs a new device login. Source: authentication tutorial.
- Lifetimes: access token 12 hours, refresh token 3 months, a new pair on every refresh, the old refresh token works for 60 seconds after a refresh. Source: authentication tutorial.
- Rate limit: 9 000 requests per minute per Client ID; above it "na minutę zablokujemy twój Client ID" with HTTP 429. Some resources use a leaky bucket per user. Retry-After is not described. Source: basic information.
- User-Agent: "NazwaAplikacji/Wersja (+AdresURL_Dokumentacji)", for example `TestApplication/1.1.0 (+https://firma.com/TestApplication-info)`; "Nazwa musi być spójna z nazwą zarejestrowanej aplikacji"; it is a whitelisting factor, do not change it except for the version. Source: Polish basic information. The plugin builds it from `appName` and `docsUrl`.
- Media types: `application/vnd.allegro.public.v1+json`; beta resources answer only `application/vnd.allegro.beta.v1+json` (a public Accept gets 406). Source: basic information, spec.
- Sandbox: API `https://api.allegro.pl.allegrosandbox.pl`, OAuth `https://allegro.pl.allegrosandbox.pl/auth/oauth`, app registration `https://apps.developer.allegro.pl.allegrosandbox.pl`, a separate account. Source: basic information.

Scopes per resource (spec, `security` of each operation):

- `GET /sale/offers`, `GET /sale/products`: `allegro:api:sale:offers:read`.
- `PUT /sale/offer-quantity-change-commands/{commandId}` and its `GET` report and `GET .../tasks`: `allegro:api:sale:offers:write` (the reads too).
- `PUT /sale/offer-price-change-commands/{commandId}` and its reports: `allegro:api:sale:offers:write`.
- `PUT /sale/offer-publication-commands/{commandId}`: `allegro:api:sale:offers:write`.
- `POST /sale/product-offers`: `allegro:api:sale:offers:write`.
- `GET /order/events`, `GET /order/event-stats`, `GET /order/checkout-forms`, `GET /order/checkout-forms/{id}`, `GET /order/checkout-forms/{id}/shipments`, `GET /order/checkout-forms/{id}/invoices`, `GET /order/customer-returns`: `allegro:api:orders:read`.
- `POST /order/checkout-forms/{id}/shipments`, `PUT /order/checkout-forms/{id}/fulfillment`, `POST /order/{orderId}/billing-documents/files`: `allegro:api:orders:write`.
- `GET /sale/issues`: `allegro:api:disputes` (the same scope covers posting messages and changing a claim status; there is no read-only variant).
- `GET /messaging/threads`: `allegro:api:messaging` (also no read-only variant).
- `GET /order/carriers`: any user or application token, no scope.

## Offers and quantities

- `GET /sale/offers`: `offer.id` is an array filter (several ids in one request), `limit` up to 1 000, `offset`, `publication.status`, `external.id`. The plugin re-reads the planned offers by `offer.id` right before a quantity or price command.
- `PUT /sale/offer-quantity-change-commands/{commandId}`, body `{"modification": {"changeType": "FIXED" | "GAIN", "value": n}, "offerCriteria": [{"type": "CONTAINS_OFFERS", "offers": [{"id": "..."}]}]}`. For `FIXED`, "a new stock quantity > 0": a quantity command cannot set zero. Up to 1 000 offers per criterion. The command id is a UUID the client generates; reusing it answers 409 "Command id was already used". 201 returns `GeneralReport` (`id`, `createdAt`, `completedAt` nullable, `taskCount` with `total`, `success`, `failed`). Rate: 250 000 offer changes per hour or 9 000 per minute per user.
- `GET /sale/offer-quantity-change-commands/{commandId}/tasks`: `limit` up to 1 000, `offset`; each task has `offer.id`, `status` (`NEW`, `SUCCESS`, `FAIL`), `message`, `errors[]`, `field`.
- Zero: `stock.available` of a product offer: "Setting this quantity to 0 for 'ACTIVE' or 'ACTIVATING' offer will trigger changing its status to 'ENDED'". The plugin ends an offer through the batch publication command instead: `PUT /sale/offer-publication-commands/{commandId}` with `{"publication": {"action": "END"}, "offerCriteria": [...]}` (actions `ACTIVATE`, `END`; the plugin never sends `ACTIVATE`).
- `endedBy` of an ended offer: `USER`, `ADMIN`, `EXPIRATION`, `EMPTY_STOCK`, `PRODUCT_DETACHMENT`, `ERROR`, `VISIBILITY`.
- `PUT /sale/offer-price-change-commands/{commandId}`: `{"modification": {"type": "FIXED_PRICE", "price": {"amount": "123.45", "currency": "PLN"}, "marketplaceId": "allegro-pl"}, "offerCriteria": [...]}`. Amounts are strings. Without `marketplaceId` the base marketplace of the offer changes. Up to 1 000 offers; 150 000 offer changes per hour or 9 000 per minute per user. Reports as for quantities.

## Orders

- `GET /order/events`: `from` ("You can use the event ID to retrieve subsequent chunks of events"), `type` (array: `BOUGHT`, `FILLED_IN`, `READY_FOR_PROCESSING`, `BUYER_CANCELLED`, `FULFILLMENT_STATUS_CHANGED`, `AUTO_CANCELLED`; the event type enum also lists `BUYER_MODIFIED`), `limit` 1 to 1 000 (default 100). Answer `{"events": [{"id", "occurredAt", "type", "order": {"checkoutForm": {"id", "revision"}, "lineItems", "buyer", "seller", "marketplace"}}]}`. Tutorial: "Możesz pobrać zdarzenia z ostatnich 60 dni", "Domyślnie otrzymasz 100 najstarszych zdarzeń", call `GET /order/events?from={last_seen_event_id}` for the next portion.
- `GET /order/event-stats`: `latestEvent.id` and `latestEvent.occurredAt`, the starting point for a fresh reader.
- Checkout form status: `BOUGHT` (no form filled in), `FILLED_IN` (payment not finished, data may change), `READY_FOR_PROCESSING` (payment completed), `CANCELLED`. Tutorial: process an order once it is `READY_FOR_PROCESSING`.
- `GET /order/checkout-forms`: `lineItems.boughtAt.gte` and `.lte`, `updatedAt.gte` and `.lte`, `status`, `fulfillment.status`, `limit` up to 100, `offset`; answer `checkoutForms`, `count`, `totalCount`.
- `GET /order/checkout-forms/{id}` fields used: `id`, `status`, `revision`, `updatedAt`, `messageToSeller`, `buyer` (`id`, `email`, `login`, `firstName`, `lastName`, `companyName`, `guest`, `phoneNumber`), `payment` (`id`, `type`: `CASH_ON_DELIVERY`, `WIRE_TRANSFER`, `ONLINE`, `SPLIT_PAYMENT`, `EXTENDED_TERM`; `finishedAt`, `paidAmount`), `fulfillment.status` (`NEW`, `PROCESSING`, `READY_FOR_SHIPMENT`, `READY_FOR_PICKUP`, `SENT`, `PICKED_UP`, `CANCELLED`, `SUSPENDED`, `RETURNED`), `delivery` (`address` with `firstName`, `lastName`, `street`, `city`, `zipCode`, `countryCode`, `companyName`, `phoneNumber`; `method.id`, `method.name`; `pickupPoint` with `id`, `name`, `description`, `address` (`street`, `zipCode`, `city`, `countryCode`); `cost`), `invoice` (`required`, `address` with `street`, `city`, `zipCode`, `countryCode`, `company` (`name`, `ids[]` with `type` such as `PL_NIP` and `value`, deprecated `taxId`), `naturalPerson` (`firstName`, `lastName`)), `lineItems[]` (`id`, `offer.id`, `offer.name`, `offer.external.id`, `quantity`, `originalPrice`, `price`, `tax.rate`, `boughtAt`), `summary.totalToPay`, `marketplace.id`.
- Payment: "paidAmount" appears only after the payment is completed; for cash on delivery it is null. Source: process orders tutorial.
- Buyer e-mail: masked, for example `ymu1woaqq+54111a037@allegrogroup.pl`. Source: process orders tutorial.
- Seller status: `PUT /order/checkout-forms/{id}/fulfillment` with `{"status": "SENT"}`, optional `checkoutForm.revision` (409 when outdated), 204 on success, 422 for a status that cannot be set ("e.g. `RETURNED` status"). `RETURNED` is set by Allegro only. The status also changes to `SENT` by itself when a tracking number is added and the seller enabled that setting.
- Parcels: `POST /order/checkout-forms/{id}/shipments` with `carrierId` (required), `waybill` (required, at most 64 characters), `carrierName` (only for `OTHER`, at most 30 characters) and `lineItems[]` (`id`; empty means the whole order). 201 answers `id`, `waybill`, `carrierId`, `carrierName`, `lineItems`, `createdAt`; 409 "Maximum waybill usage exceeded". `GET /order/checkout-forms/{id}/shipments` lists the parcels, including those added in the seller panel or by the carrier. 50 requests per second.
- Carriers: `GET /order/carriers` answers `carriers[]` with `id` and `name`. Ids seen in the spec example and the news: `POCZTA_POLSKA`, `DHL`, `YUN_EXPRESS`, `UPS`, `INPOST`, `OTHER` ("It’s highly recommended to use an identifier different from `OTHER`"). The plugin reads the list at run time and never hardcodes the others.
- Invoices: the two-step `POST /order/checkout-forms/{id}/invoices` (metadata) then `PUT /order/checkout-forms/{id}/invoices/{invoiceId}/file` (raw PDF, `application/pdf`, 413 above 3 MB) are both `deprecated: true` in the spec. The current call is `POST /order/{orderId}/billing-documents/files`: `multipart/form-data` with `file` (PDF only) and `invoiceNumber`, one request ("instead of the two-step flow"); 201 answers `id`; 409 "Order with given id already has an invoice with the same file name, or an invoice file has already been uploaded for this order"; 413 "Max file size is 3MB"; 422 covers an invalid PDF and "the maximum number of invoices for this order has been reached"; 429 "Wait a few seconds before adding the next one". There is no idempotency key, so the plugin reads `GET /order/checkout-forms/{id}/invoices` (`invoices[]` with `id`, `invoiceNumber`, `createdAt`, `file`) before every upload.
- Customer returns: `GET /order/customer-returns` is BETA (`application/vnd.allegro.beta.v1+json`), filters `orderId`, `status`, `createdAt.gte` and `.lte`, `from`, `limit` up to 1 000, `offset`; answer `count`, `customerReturns[]` with `id`, `createdAt`, `referenceNumber`, `orderId`, `items[]` (`offerId`, `quantity`, `name`, `price`, `reason`), `status` (`CREATED`, `DISPATCHED`, `IN_TRANSIT`, `DELIVERED`, `FINISHED`, `FINISHED_APT`, `REJECTED`, `COMMISSION_REFUND_CLAIMED`, `COMMISSION_REFUNDED`, `WAREHOUSE_DELIVERED`, `WAREHOUSE_VERIFICATION`), `marketplaceId`. 25 requests per second per user.

## Post-purchase issues and messages

- The current spec has no `/sale/disputes` path at all; disputes and claims are read through `GET /sale/issues` (beta media type in every example of the discussions tutorial). Parameters `checkoutForm.id`, `limit` 1 to 100 (default 10), `offset`, `status` (array: `DISPUTE_CLOSED`, `DISPUTE_ONGOING`, `DISPUTE_UNRESOLVED`, `CLAIM_SUBMITTED`, `CLAIM_ACCEPTED`, `CLAIM_REJECTED`). Each issue: `id`, `type` (`DISPUTE`, `CLAIM`), `referenceNumber` (claims), `decisionDueDate` (claims), `openedDate`, `subject` (a code such as `NO_PRODUCT_RECEIVED`), `checkoutForm.id`, `currentState` (`status`, `statusDueDate`, `returnRequired`, `chatActive`), `chat.lastMessage.status` (`NEW`, `SELLER_REPLIED`, `BUYER_REPLIED`, `ALLEGRO_ADVISOR_REPLIED`), `chat.messagesCount`, `right` (`WARRANTY`, `COMPLAINT`). The plugin stores codes, dates and ids only, never the description or the chat.
- `GET /messaging/threads`: `limit` 1 to 20, `offset` (public media type), sorted by last message, newest first; each thread `id`, `read`, `lastMessageDateTime`, `interlocutor`. The `read` filter exists only in the beta media type. The plugin counts unread threads among the newest 100 (five pages) with the public media type.

## Catalog products and new offers

- `GET /sale/products?phrase={ean}&mode=GTIN&language=pl-PL` finds a catalog product by EAN ("At least ean or phrase parameter is required"; `mode` `GTIN` restricts the search to GTINs). Answer `products[]` with `id`, `name`, `category.id`, `publication.status` (`PROPOSED`, `LISTED`). Leaky bucket.
- `POST /sale/product-offers`: minimal body `productSet[].product.id` (with `idType` `GTIN` when the id is an EAN), `sellingMode.price` (`amount`, `currency`), `stock.available`. Without `publication.status` "the system will activate the offer immediately"; the plugin always sends `"publication": {"status": "INACTIVE"}`, a draft. Also used: `external.id` (at most 100 characters), `delivery.shippingRates` (id or name), `location` (`city`, `countryCode`, `postCode` in `XX-XXX` for PL, `province` mandatory for PL: `DOLNOSLASKIE` ... `ZACHODNIOPOMORSKIE`), `payments.invoice` (`VAT`, `VAT_MARGIN`, `WITHOUT_VAT`, `NO_INVOICE`). 201 means processed, 202 means accepted for asynchronous processing (status under `GET /sale/product-offers/{offerId}/operations/{operationId}` from the `Location` header).

## The Medusa side (read in @medusajs/core-flows 2.15.3, exercised on a local Medusa 2.15.3)

- `createOrderWorkflow` ("create-orders", the deprecated alias `createOrdersWorkflow` is the same function) takes `unit_price` with `is_tax_inclusive`, `status`, `is_draft_order`, `no_notification` and our shipping methods, runs `updateOrderTaxLinesWorkflow` without forcing (tax lines only when the region has automatic taxes), does not reserve inventory and emits no event.
- `convertDraftOrderWorkflow` takes a lock on the order id, validates the draft, reserves inventory with `reserveInventoryStep` in the stock locations of the order's sales channel, sets `pending` and `is_draft_order: false`, then emits `order.placed` (priority critical).
- `updateOrderTaxLinesWorkflow` ADDS tax lines (`upsertOrderLineItemTaxLines` without ids); run over lines that already have them it doubles the VAT. The import forces it only for lines without any.
- `markPaymentCollectionAsPaid` captures through `capturePaymentWorkflow`, which emits `payment.captured`.
- Query: asked for `total` together with a few item fields (`items.id`), the order total comes out as the shipping alone because the items are loaded without their quantities; `total` alone, or with `items.*`, is right. Right after creation in the same process, `items.quantity` asked alone can come back empty; `items.detail.quantity` and `items.raw_quantity` carry it.
- Locking module, in-memory provider: `acquire(key, { ownerId, expire })` without `awaitQueue` throws when another owner holds the key (a try-lock); `release(key, { ownerId })` frees it. The import takes `marketplace-order-ref:<ref>` the same way the BaseLinker plugin does.
