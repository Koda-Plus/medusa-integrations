# Fakturownia API: what this plugin relies on, and where it is documented

Checked on 2026-10-05 (version 0.1.0) and again on 2026-10-06 (version 0.2.0) against:

- the official API repository, https://github.com/fakturownia/API (README.md and KSeF.md, last change 2026-09-07 at both checks);
- the official examples page linked from that README, https://app.fakturownia.pl/api;
- the official e-receipt API of the same vendor, https://github.com/e-paragony/api (README.md), which calls the Fakturownia API;
- the help of InvoiceOcean, the same platform under its international name, https://invoiceocean-help.sugester.com/479474-Changing-the-format-of-invoice-numbering;
- Fakturownia's own pages, for the setup guide: https://fakturownia.pl/cennik, https://fakturownia.pl/integracja-z-ksef, https://fakturownia.pl/funkcja-powiadomienia-sms and https://fakturownia.pl/blog/4-sposoby-aby-przyspieszyc-obsluge-platnosci-w-twojej-firmie;
- for returns of goods sold with a receipt, the official text of the cash register regulation from the ELI API of the Sejm, https://api.sejm.gov.pl/eli/acts/DU/2025/845/text.pdf;
- for the Medusa side, the event and order types of the installed Medusa 2.15.3 (`@medusajs/utils`, `@medusajs/types`), the source of https://docs.medusajs.com/resources/references/events.

Points marked "measured" come from the production Fakturownia integration Koda Plus runs for a Polish cosmetics wholesaler; they are not in the documentation. Nothing in 0.2.0 was tried against a real account: what the documentation does not say is marked as such, and the plugin is built not to depend on it.

## Authentication

- Documented three ways: `api_token` in the query string (GET examples), `"api_token"` in the JSON body (POST and PUT examples), and the header `Authorization: Bearer API_TOKEN` (app.fakturownia.pl/api, XML examples; e-paragony README, JSON examples for `GET /invoices.json`, `POST /invoices.json` and `send_by_email`).
- The plugin sends the header only. The token is never in a URL or a body, and redirects are not followed (one exception, the KSeF files below, follows a redirect by hand).
- Where the token is: "`API_TOKEN` token trzeba pobrać z ustawień aplikacji ("Ustawienia -> Ustawienia konta -> Integracja -> Kod autoryzacyjny API")" (README.md, authentication). The setup guide and the FAQ give this path.

## Documents

- Create: `POST /invoices.json` with `{"invoice": {...}}`; the examples treat HTTP 201 as success and the answer is the document (with `id` and `number`). `number: null` or no number: the account numbering assigns one. The plugin never sends a number.
- Read: `GET /invoices/{id}.json`; `fields[invoice]=a,b,c` limits the answer (KSeF.md, "Sprawdzanie statusu wysyłki").
- Update: `PUT /invoices/{id}.json` with the fields to change (partial). Measured: `{"invoice": {"paid": "143.00"}}` marks a document paid, also a proforma, while `status: "paid"` is refused on a proforma with HTTP 422.
- Status: `POST /invoices/{id}/change_status.json?status=STATUS`, statuses `issued`, `sent`, `paid`, `partial`, `rejected`. Measured: `rejected` works on a proforma even when it is the last document of its numbering, where `POST /invoices/cancel.json` is refused.
- E-mail: `POST /invoices/{id}/send_by_email.json`, see "E-mail" below.
- PDF: `GET /invoices/{id}.pdf`. Measured: a fresh document can answer 422 for a few seconds, and a KSeF account shows an HTML page instead of the VAT invoice PDF until the KSeF number arrives. The public `token` links (`/invoice/{token}.pdf`) open a document without login and are not used.
- Proforma to VAT: `from_invoice_id` is "id faktury na podstawie której faktura została wygenerowana". Measured: it only links the documents and copies nothing (a payload of `kind` and `from_invoice_id` alone is refused with 422), so the plugin copies the proforma's positions and buyer, including `buyer_company`, `buyer_first_name` and `buyer_last_name`. The documented `copy_invoice_from` would copy the whole proforma, its dates included, and is not used.
- `internal_note`: "treść notatki prywatnej na fakturze, niewidoczna na wydruku" (README.md, fields of an invoice). The plugin writes its marker for a correction there (see "Corrections").

## Order number, lookups and exactly once

- `oid`: "numer zamówienia (np z zewnętrznego systemu zamówień)", printed on the document.
- `oid_unique: "yes"`: "system nie pozwoli stworzyc 2 faktur o takim samym OID". Whether the rule is per kind or per account is not documented, so it is left out for a final document made from a proforma and for a correction (both carry the order number of their original), and it is never the only lock.
- Lookup by order number: `GET /invoices.json?oid=nr_zam` ("Pobranie faktury po Id zamówienia", app.fakturownia.pl/api); README section "Kompatybilność wsteczna, pole oid": "zapis, odczyt i wyszukiwanie faktur po oid działają jak dotychczas". Whether the filter is exact is not documented, so the plugin matches the order number and the kind exactly on its side and reads page after page with a ceiling.
- Documents made from another one: `GET /invoices.json?from_invoice_id=id` ("Pobieranie faktur, które zostały wygenerowane na podstawie dokumentu o podanym Id"), and the other way round `GET /invoices.json?invoice_id=id` ("Pobieranie faktur, na podstawie których został wygenerowany dokument o podanym Id"), both on app.fakturownia.pl/api.
- List parameters used: `page`, `per_page` (100 at most), `period=more` with `date_from` and `date_to` (or `period=all`), `kind`.

## Fields of a document

- `kind`: `vat`, `proforma`, `bill`, `receipt`, `advance`, `final`, `correction`, `invoice_other`, `vat_margin`, `kp`, `kw`, `estimate`, `vat_mp`, `vat_rr`, `correction_note`, `accounting_note`, `client_order`, `dw`, `wnt`, `wdt`, `import_service`, `import_service_eu`, `import_products`, `export_products`. A receipt is `receipt` (also in the e-paragony README); `receiptKind` can change it.
- `lang`: `pl`, `en`, `en-GB`, `de`, `fr`, `cz`, `ru`, `es`, `it`, `nl`, `hr`, `ar`, `sk`, `sl`, `el`, `et`, `cn`, `hu`, `tr`, `fa`, or two joined by a slash for a bilingual document (`pl/en`).
- `department_id`: the seller company or department; without it (and without `seller_name`) the main company of the account. Where to find it: "w menu Ustawienia > Dane firmy należy kliknąć na firmę/dział i ID działu pojawi się w URL" (README.md, fields of an invoice). 0.2.0 picks it per sales channel (`departmentsBySalesChannel`) and "Check connection" reads `GET /departments.json` to confirm every id.
- `category_id`, `place`. Measured: `place` is not taken from the account settings through the API.
- Buyer: `buyer_name`, `buyer_company` ("czy klient jest firmą"), `buyer_first_name`, `buyer_last_name`, `buyer_tax_no`, `buyer_tax_no_kind` (set to `nip_ue` by Fakturownia for a tax number with another EU country prefix), `buyer_email`, `buyer_street`, `buyer_post_code`, `buyer_city`, `buyer_country`. KSeF.md: always send `buyer_company`, it decides the automatic sending to KSeF; for a person (`buyer_company=false`) `buyer_first_name` and `buyer_last_name` are required. Measured: without `buyer_company` the buyer is created as a company.
- Positions: `name`, `code`, `quantity`, `quantity_unit`, `total_price_gross`, `tax` (a rate, or `zw`, `np`), optionally `price_gross`, `discount_percent`, `discount`. Measured: `total_price_gross` is required (422 without it).
- Discounts: `discount_kind` is `percent_unit`, `percent_unit_gross`, `percent_total` or `amount`; per the README a position discount is computed only with `show_discount` set, and app.fakturownia.pl/api shows it together with `discount_kind: "percent_unit"`. Measured: without both, `discount_percent` is silently dropped. The plugin sends discounts inside the gross totals and adds these two fields only when it copies positions that carry a discount.
- Payment: `payment_type` (`transfer`, `card`, `cash`, `cash_on_delivery`, `payu`, `paypal`, `off`, or free text), `payment_to_kind` (a number of days, `off`, `other_date` with `payment_to`, or `description`), `paid` (the amount paid), `status`.
- Currency: `currency`; a conversion is documented with `exchange_currency` (like "PLN"), `exchange_kind` (`ecb`, `nbp`, `cbr`, `nbu`, `nbg`, `own`), `exchange_currency_rate` and `exchange_note` (README.md, fields of an invoice). The plugin sends the order's currency and no conversion (listed under "What this plugin does not do").
- Errors: HTTP 422 with `{"code": "error", "message": {"field": ["- message"]}}` (KSeF.md).

## Corrections (0.2.0)

- Create: `POST /invoices.json` with `kind: "correction"`, `correction_reason`, `invoice_id` and `from_invoice_id` (both the id of the corrected invoice), and per position `kind: "correction"`, the difference in `quantity` and `total_price_gross`, `correction_before_attributes` (`kind: "correction_before"`) and `correction_after_attributes` (`kind: "correction_after"`), each with `name`, `quantity`, `total_price_gross` and `tax` (README.md, "Dodanie nowej faktury korygującej" and section "Faktura korekta"). The plugin sends exactly this shape, with a position only for what changed, and `quantity_unit` and `code` as on the original.
- Read: `?correction_positions=full` returns positions with "przed / po korekcie"; `additional_fields[invoice]=corrected_content_before,corrected_content_after` returns the texts "Treść korygowana" and "Treść poprawiona" (README.md, "Faktura korekta"). Not used: the plugin keeps its own before and after.
- With KSeF (KSeF.md, "Korekty faktur"): creating a correction works as without KSeF, but `invoice_id` must point to an existing invoice, and these fields must not change against the corrected invoice: `department_id`, `seller_tax_no`, `seller_email`, `seller_phone`, `seller_fax`, `seller_www`, `seller_tax_no_kind`, `seller_bdo_no`, `buyer_company`, `buyer_tax_no`, `buyer_note`, `buyer_email`, `buyer_phone`, `buyer_mobile_phone`, `buyer_tax_no_kind`, `use_invoice_issuer`, `invoice_issuer`, `use_delivery_address`, `delivery_address`. The plugin therefore reads the corrected invoice and copies its buyer, `department_id`, `oid`, currency, language, category, place, payment type and sell date into the correction, and sends no seller fields at all (the department supplies them, as on the original).
- `gov_corrected_invoice_number`: the KSeF number of the corrected invoice, filled in by Fakturownia on a correction (KSeF.md). The plugin shows it.
- "W KSeF nie można usunąć faktury - jedynym sposobem "anulowania" jest wystawienie korekty do zera" (KSeF.md, "Korekty faktur"). A canceled order with an issued VAT invoice therefore gets a correction to zero, planned for approval.
- `correction_reason` holds at most 256 characters on a correction (KSeF.md, "Ograniczenia długości pól"). The admin field takes at most 256 characters and counts them down; the payload is cut to 256 as well.
- Exactly once: the API has no idempotency key. The plugin writes `[medusa:<row id>]` into `internal_note` (private, not printed, see "Documents") and, before every create, looks for a correction carrying that marker among `GET /invoices.json?from_invoice_id=<corrected invoice>` and among `GET /invoices.json?oid=<order>&kind=correction` in a date window. Whether `?from_invoice_id=` lists corrections is not documented (a correction carries `from_invoice_id` per the example above), hence the second lookup; the marker, the corrected invoice and the amount are compared on the plugin's side.
- Receipts: the API documents an invoice issued for an existing receipt (`from_invoice_id` of the receipt with `additional_params: "for_receipt"`, README.md, "Dodawanie faktury do istniejącego paragonu"), and no correction of a receipt. For a receipt the plan is manual (see "Returns of goods sold with a receipt").

## Returns of goods sold with a receipt (law, not API)

- Rozporządzenie Ministra Finansów z dnia 25 czerwca 2025 r. w sprawie kas rejestrujących (Dz.U. 2025 poz. 845), in force; it replaced the regulation of 29 April 2019 (Dz.U. 2019 poz. 816), repealed on 2025-07-01 (status from https://api.sejm.gov.pl/eli/acts/DU/2019/816 and https://api.sejm.gov.pl/eli/acts/DU/2025/845).
- § 3 ust. 2: returns of goods and accepted complaints are not recorded in the sales register of the cash register. § 3 ust. 3: those that return all or part of the payment go into a separate register of returns and accepted complaints with the date of sale, the name of the goods, the date of the return, the gross value and the VAT (or the returned amount and its VAT for a partial return), the sales document (for a receipt its number and unique number) and "protokół przyjęcia zwrotu towaru lub reklamacji towaru lub usługi podpisany przez sprzedawcę i nabywcę albo notatkę służbową lub protokół z nabycia sprawdzającego".
- So a receipt's plan shows the amounts for that register and a person marks it done; when an invoice was issued for the receipt, that invoice is corrected in Fakturownia by hand.

## E-mail (0.2.0)

- `POST /invoices/{id}/send_by_email.json` sends the document to the e-mail given on the invoice ("na e-mail klienta podany przy tworzeniu faktury, pole "buyer_email""). Optional parameters (README.md, "Wysłanie faktury e-mailem do klienta"): `email_to=email1,email2,email3` ("Można ustawić w ten sposób do 5 adresów email"), `email_cc=` (a copy), `email_pdf=true` (the PDF attached), `update_buyer_email=true` (with `email_to`, changes the buyer's e-mail on the invoice, or `recipient_email` when the invoice has a recipient), and `print_option` for the PDF (`original`, `copy`, `original_and_copy`, `duplicate`).
- The plugin sends `email_to` (at most five addresses, checked before the request) and `email_pdf`, as query parameters. It never sends `update_buyer_email`: the invoice must not change, and on a KSeF correction `buyer_email` must stay as on the original.
- With KSeF active, a company document can be e-mailed only after its KSeF number; the refusal is HTTP 200 with `{"status": "error", "message": "Faktura nie może zostać wysłana - brak numeru KSeF"}` (KSeF.md, "Wysyłanie faktur emailem do klientów"). In the KSeF DEMO environment e-mails are not blocked (KSeF.md, "Tryb DEMO").
- No documented parameter of `send_by_email` sets the subject or the text of the e-mail: the account's template applies.
- Payment reminders: the API documents no call to send a reminder. The only related field is `disable_auto_reminders` of a client ("nie wysyłaj automatycznych przypomnień", README.md, "Klienci"). Reminders are an account feature: "Przypomnienia wysyłane są automatycznie dla każdej nierozliczonej faktury, po terminie płatności, w zdefiniowanym czasie", with an editable subject and template (fakturownia.pl blog, "4 sposoby, aby przyspieszyć obsługę płatności w Twojej firmie"), and SMS reminders before, on and after the payment date (https://fakturownia.pl/funkcja-powiadomienia-sms). So "Send a reminder" in the plugin is the document e-mailed again with `send_by_email`, at most once a day, and the admin says that Fakturownia's own reminders send their own text.
- A request without an answer may have sent the e-mail: the plugin never repeats it on its own.

## KSeF

- Fields (KSeF.md, "Opis wszystkich pól KSeF"): `gov_status`, `gov_id` (the KSeF number, `{NIP}-{DATA}-{ID}`), `gov_send_date`, `gov_sell_date`, `gov_error_messages` (an array, or null for no errors or no validation), `gov_verification_link` (`https://ksef.mf.gov.pl/web/verify/{gov_id}/{hash}`), `gov_link`, `gov_corrected_invoice_number`. The plugin reads all but `gov_sell_date`.
- `gov_status` (KSeF.md, "Możliwe statusy"): `ok`, `processing`, `send_error` ("sprawdź gov_error_messages"), `server_error` ("spróbuj ponownie później"), `status_check_error` ("faktura mogła już zostać przyjęta"), `offline` (waiting to be sent), `offline_error`, `duplicate_error` ("faktura o tym numerze jest już w KSeF"), `blocked_403_error` (no permission to send), `not_applicable`, `not_connected` (no authorization), `null` (not sent); the KSeF test environment reports the same values with a `demo_` prefix, except `null`.
- Sent to KSeF: `vat`, `correction`, `vat_mp`, `vat_margin`, `wdt`, `export_products`, `advance`, `final`. Proformas and receipts get `not_applicable`.
- Sending: the account's automatic setting sends documents (below). "Send to KSeF again" uses `GET /invoices/{ID}.json?send_to_ksef=yes` (KSeF.md, "Ręczne wysłanie istniejącej faktury"), which answers the document with `gov_status: "processing"`. The plugin offers it only for a document never sent and for `send_error`, `server_error`, `offline`, `offline_error`, `not_connected` and `blocked_403_error`, never for `status_check_error` (the invoice may be accepted already) or `duplicate_error`, sends it once (a second call could make a duplicate), at most once per five minutes per document. `gov_save_and_send` (on a create or an edit) is not used.
- Files (KSeF.md, "Pobieranie dokumentów KSeF" and "Pobranie XML faktury KSeF i UPO"): `GET /invoices/{ID}/attachment?kind=gov` (the KSeF XML, `text/xml`) and `?kind=gov_upo` (the UPO), available once `gov_status` is `ok`, at once for interactive sending and within an hour for batch sending; "HTTP 302 - przekierowanie do pobierania pliku (plik jest gotowy)", "HTTP 404 - brak danego pliku dla tej faktury". The plugin follows the 302 by hand, to https only, and sends the token along only when the file stays on the account's host.
- After KSeF accepted a document in production, editing and deleting it are blocked and changes are made only with correction invoices; in the DEMO environment nothing is blocked (KSeF.md, "Włączanie KSeF w Fakturowni").
- Field limits (KSeF.md, "Ograniczenia długości pól"): `positions[].name` 256, `buyer_phone` and `seller_phone` 16, `buyer_email` and `seller_email` 255, `correction_reason` 256 characters. The demo's KSeF rejection is the documented example "Telefon klienta - pole jest za długie (maksymalna ilość znaków: 16)" (KSeF.md, "Sprawdzanie błędów walidacji"), and the demo's refused document is the documented 422 for `exempt_tax_kind` ("- nie może być puste").
- A document dated before today is treated as OFFLINE24, so the plugin dates documents in Poland's time zone (Europe/Warsaw), not in UTC.
- A KSeF number triggers the account's standard webhooks (KSeF.md). Not used: the plugin reads the status every 15 minutes.

## KSeF setup in Fakturownia (for the setup guide)

- Connection (KSeF.md, "Włączanie KSeF w Fakturowni"): production under "Ustawienia → Integracje i dodatki → KSeF", the test environment under "KSeF (DEMO)" in the same menu: activate the integration, choose the NIP, authorize with certificates or an authorization file, configure.
- Automatic sending (KSeF.md, "Konfiguracja automatycznej wysyłki"): set in the interface, not through the API, under "Ustawienia → KSeF", section "Automatyczna wysyłka", `gov_auto_send_mode`: off (`null`), only companies from Poland (`pl_companies`), all companies (`all_companies`), companies and private persons (`all`). The first two send only documents with `buyer_company=true`.
- "Zablokuj tworzenie faktur niezgodnych z KSeF" (`validate_invoices_for_gov`, KSeF.md, "Ustawienie validate_invoices_for_gov"), on by default: a document that does not meet KSeF's rules is not saved and the API answers 422 with the list; off: it is saved with `gov_error_messages` and the automatic sending fails. The guide recommends leaving it on.
- Price (https://fakturownia.pl/cennik): "Testuj za darmo przez 30 dni!", a free Micro plan with 3 invoices a month, "Integracja z KSeF" in every plan; https://fakturownia.pl/integracja-z-ksef calls the KSeF integration full and free regardless of the plan, with no extra fee.

## Medusa (0.2.0)

- Event payloads (`@medusajs/utils` 2.15.3, `dist/core-flows/events.d.ts`): `order.return_received` `{ order_id, return_id }`, `payment.refunded` `{ id }` (the payment), `order-edit.confirmed` `{ order_id, actions }` (since 2.8.0), `order.canceled` `{ id }`. The plugin plans corrections from these and from a scan, since events can be missed.
- Quantities after returns: the order item detail (`OrderItemDTO` in `@medusajs/types` 2.15.3) carries `quantity`, `return_received_quantity`, `return_dismissed_quantity` and `written_off_quantity`. Goods that came back are received plus dismissed (damaged) returns.
- The order's `version` ("The version of the order", `OrderDTO`) is kept on each document, to see what changed after issue; refunds come from `payment_collections.payments.refunds`.
- Store routes authenticate the customer with `authenticate("customer", ["session", "bearer"])` from `@medusajs/framework/http` (the plugin's `src/api/middlewares.ts`); the routes take the customer id from `auth_context` (actor type `customer`, `actor_id`) and compare it with the order's `customer_id`.

## Other

- Harmless reads for "Check connection": `GET /departments.json`, `GET /categories.json`.
- Rate limits: not documented in any of the sources above. The plugin limits itself to 60 requests per minute by default (`requestsPerMinute`).
- Numbering: not part of the API documentation. InvoiceOcean help: "Settings > Account Settings > Documents numbering tab", the format variables `nr`, `nr-m`, `nr-d`, `yyyy`, `yy`, `mm`, `dd` with examples like "1/01/2011"; whether each document kind has its own format is not said there. Documents of a production account look like "52/08/2026" (number within the month, month, year). The demo adds a prefix per kind ("FV 12/10/2026", "PRO 3/10/2026", "PAR 7/10/2026", "KOR 1/10/2026") so the kinds read at a glance; a real account returns whatever format it is set to.
- Alternatives (checked on 2026-10-06): the npm registry search for "fakturownia" and "fakturownia medusa" lists no Medusa plugin for Fakturownia (a generic Node.js client, `fakturownia-sdk`, and n8n nodes exist); the catalog behind https://medusajs.com/integrations lists "inFakt Invoicing" ("inFakt invoices and KSeF filing") and "Invoices" ("Auto-generate PDF invoices and credit notes"), none for Fakturownia.
- The brand mark in `brand-source/` was fetched from the head and the header of https://fakturownia.pl on 2026-10-05: `fakturownia-logo.svg` (https://fs.siteor.com/radgost/files/marketing-2023/img/fakturownia-logo.svg), `favicon-160x160.png` and `apple-touch-icon-152x152.png` (https://fs.siteor.com/radgost/files/marketing-2023/favicon/).
